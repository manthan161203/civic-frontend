# `@civic/api-types`

One description of the Civic HTTP API, shared by `admin/` (Next.js 16) and
`mobile/` (Expo 54 / React Native 0.81).

The backend's own OpenAPI document is the source of truth. Nothing here is
hand-written except the two access manifests, which encode things OpenAPI cannot
express.

Generated from `civic-backend` — **178 operations, 88 schemas**.

---

## Layout

```
packages/api-types/
├── openapi.json                 snapshot of the backend spec (key-sorted, diffable)
├── src/
│   ├── schema.d.ts              GENERATED by openapi-typescript — 12.3k lines, never edit
│   ├── models.d.ts              GENERATED — 80 model aliases + 6 multipart bodies
│   ├── helpers.d.ts             RequestBody / ResponseBody / QueryParams / PathParams
│   ├── endpoint-access.js/.d.ts GENERATED from backend source — role + surface per route
│   ├── field-access.js/.d.ts    HAND-MAINTAINED — admin-only vs mobile-user fields
│   ├── __typetest__.ts          compile-time tests; `tsc --noEmit` is the assertion
│   └── index.d.ts / index.js    barrel
└── scripts/
    ├── generate.mjs             spec → schema.d.ts + models.d.ts (+ `--check` for CI)
    └── derive-endpoint-access.py  backend AST → endpoint-access.js
```

Why two generators: role gating lives in FastAPI `Depends(require_role(...))`
declarations, which never reach the OpenAPI document. `schema.d.ts` can tell you
`POST /admin/admins` takes a `CreateSubAdminRequest`; only the Python AST can
tell you a `ward_admin` may not call it.

---

## Using it

Both apps are plain JavaScript, so these types are **editor-level today** — full
IntelliSense and go-to-definition via JSDoc, with no build step and no runtime
cost, but no enforcement until a file opts in with `// @ts-check` or the app
enables `checkJs`. That is a deliberate first step; it makes the types useful
immediately without asking either app to migrate.

```js
/** @typedef {import('@civic/api-types').IssueResponse} IssueResponse */
/** @typedef {import('@civic/api-types').IssueListResponse} IssueListResponse */

/** @param {import('@civic/api-types').IssueCreate} body */
export const createIssue = (body) => api.post('/issues', body);
```

Naming the route instead of the model, so a backend rename breaks the call site:

```ts
import type { RequestBody, ResponseBody, QueryParams } from '@civic/api-types';

type Body  = RequestBody<'/issues', 'post'>;   // IssueCreate
type Res   = ResponseBody<'/issues', 'get'>;   // IssueListResponse
type Query = QueryParams<'/issues', 'get'>;    // { page?, size?, status?, … }
```

Method names are checked too: `ResponseBody<'/issues/{issue_id}', 'delete'>` is a
compile error, because that route does not exist.

Runtime guards:

```js
import { ENDPOINT_ACCESS, ADMIN_ROLES } from '@civic/api-types';

const { roles } = ENDPOINT_ACCESS['POST /admin/admins'];
// roles -> ['admin', 'district_admin', 'taluka_admin']
```

### Wiring (not done yet — needs a decision)

There is no root `package.json`, so the two apps do not currently share a
dependency graph. Two ways to fix that:

**A. npm workspaces (recommended).** Add a root `package.json` with
`"workspaces": ["admin", "mobile", "packages/*"]`, then `"@civic/api-types": "*"`
in each app. Standard, and both Next 16 and Expo 54 support it — Expo needs the
documented monorepo `metro.config.js` additions (`watchFolders`,
`disableHierarchicalLookup`).

**B. Path alias only.** Add `"@civic/api-types": ["../packages/api-types/src"]`
to each app's `jsconfig.json` `paths`. No install, no hoisting risk; Metro needs
`watchFolders` for the out-of-root directory either way.

I have not touched `admin/package.json`, `mobile/package.json`, or either Metro
config — rewiring two build systems is a bigger change than generating the
package, and A vs B is your call.

## Regenerating

```bash
npm run generate            # against a running backend on :8000
npm run generate --from ./openapi.json   # offline, from the snapshot
npm run generate:access     # re-derive roles from ../../civic-backend source
npm run typecheck           # runs the compile-time tests
```

In CI, against a live backend:

```bash
npm run check   # non-zero exit if the committed types drift from the API
```

That is the frontend counterpart to the backend's `alembic check`. It is the
mechanism that stops this package from quietly going stale.

> `endpoint-access.js`'s `surfaces` column is a call-site scan of both apps, so
> it is a heuristic: a route mentioned in a JSDoc `@example` counts as called.
> `POST /issues` is currently marked `["admin","mobile"]` for that reason — only
> mobile really posts issues.

**Better long-term fix:** emit `x-roles` per operation from the backend's
`custom_openapi()`. Then `derive-endpoint-access.py` deletes itself and roles
come from the same generation pass as everything else.

## Admin-only vs mobile-user fields

This is the part a generated types package cannot give you, and the reason
`field-access.js` exists.

**The backend does not vary serialization by role.** `IssueResponse.model_validate(issue)`
emits the same 45 keys to a citizen and to a super-admin. So there is exactly one
TypeScript type per model, correctly — the difference is in which fields are
*writable*, which are *meaningful*, and which are *silently discarded*.

### Request fields — who may set what

| Model | Field | Allowed roles | If someone else sends it | Surface |
|---|---|---|---|---|
| `UpdateProfileRequest` | `ward_id` | `citizen` only | **403** | mobile |
| `UpdateProfileRequest` | `taluka_id`, `district_id` | — | **removed from the schema** | — |
| `IssueCommentCreate` | `is_internal` | worker + all admins | **silently downgraded to `false`** | admin |
| `IssueUpdate` | `status`, `resolution_notes` | worker + all admins | ignored | both |
| `IssueUpdate` | `assigned_worker_id` | admins only | ignored | admin |
| `IssueUpdate` | `citizen_rating` | `citizen` only | ignored | mobile |
| `IssueUpdate` | `priority`, `department` | **nobody** | **ignored — never implemented** | none |
| `IssueCreate` | `severity`, `priority`, `department`, `is_sos` | **anyone**, incl. citizens | — | mobile |
| `CreateSubAdminRequest` | `ward_id` / `taluka_id` / `district_id` | tiered by caller's own scope | 403 | admin |
| `CreateWorker` | `ward_id` / `taluka_id` / `district_id` | tiered by caller's own scope | 403 | admin |

Three of these deserve emphasis:

- **`IssueUpdate.priority` and `IssueUpdate.department` are declared, documented
  as admin-only, and never read by the handler.** `PATCH /issues/{id}` returns
  200 and changes nothing. Do not build UI against them; `POST /admin/issues/bulk`
  with `action: "priority"` does work.
- **`is_internal` fails silently.** A citizen posting an internal note gets 201
  and a public comment. The mobile UI must not offer the control, because the
  response cannot be distinguished from success.
- **`IssueCreate.severity` / `priority` are not gated at all.** They read like
  admin triage fields but any citizen sets them freely at creation. Treat them as
  user-supplied hints; the AI classifier writes its own view to `ai_*`.

### Response fields — who they are *for*

Same shape everywhere; nulls mean "not applicable to you", not "withheld".

| Model | Admin-oriented | Mobile-user-oriented |
|---|---|---|
| `IssueResponse` | block workflow (`is_blocked`, `blocked_by_id`, `admin_unblock_note`, `blocked_duration_hours`, …), escalation (`is_escalated`, `escalation_level`), `reassignment_count`, `is_duplicate`, `parent_issue_id`, `is_deleted`, and all 7 `ai_*` triage fields | `user_upvoted`, `upvote_count`, `comment_count`, `citizen_rating` |
| `UserResponse` | `taluka_id`, `district_id`, `department` | `ward`, `ward_id`, `aadhar_verified`, `google_id`; worker: `is_online`, `is_available`, `latitude`, `longitude` |
| `IssueCommentResponse` | `is_internal` | — |

### Two things that are not field differences

**`GET /issues/{id}/comments` returns different *rows* per role.** Citizens have
internal notes *and every worker-authored comment* filtered out. Identical
TypeScript type, different cardinality — so one app's cached result must never be
reused for the other.

**`IssueResponse.reporter` leaks a phone number.** It is
`Optional[IssueReporterInfo]` with `from_attributes`, over an eager ORM
relationship, so `model_validate` emits `{id, name, phone}` unconditionally.
Verified by constructing the model directly against the running backend: every
`GET /issues`, `/issues/{id}`, `/issues/nearby` and `/issues/search` hands the
reporter's phone number to any authenticated caller, including unrelated
citizens. Neither app renders it, but it is on the wire. **This needs a backend
fix** — a role-conditional serializer or a separate public response model — not a
client-side omission.

### Where the two surfaces must not share code

| Action | Admin | Mobile |
|---|---|---|
| list issues | `GET /admin/issues` (jurisdiction-scoped, `severity`/`department` filters) | `GET /issues` (reporter-scoped, `sort` param) |
| assign a worker | `POST /admin/issues/{id}/assign` | — |
| resolve an issue | `PATCH /issues/{id}` `{status:'resolved'}` | `POST /workers/tasks/{id}/resolve` (multipart, after-photo required) |
| delete an issue | `DELETE /admin/issues/{id}` | — (no `DELETE /issues/{id}` exists) |
| leaderboard | `GET /admin/workers/leaderboard`, `GET /public/leaderboard` | `GET /leaderboard/{citizens,workers}` |

Both list endpoints return `IssueListResponse`, which is exactly why they should
not share a fetch layer: the type will not stop you from calling the wrong one.

The resolve split matters most — the worker route enforces the after-photo
requirement and runs AI resolution verification; the admin `PATCH` does neither.

## Contract gaps this package makes visible

Encoded as `@ts-expect-error` assertions in `src/__typetest__.ts`, so they cannot
be forgotten:

- **`PATCH /admin/announcements/{id}` does not exist.** `admin/src/api/index.js:76`
  calls it from the announcements edit flow; it 405s.
- **`DELETE /issues/{id}` does not exist.** Implied by a JSDoc `@example` in
  `admin/src/api/client.js`. The real route is `DELETE /admin/issues/{id}`.
- **`POST /workers/tasks/{id}/block` takes `reason` as a query parameter**, not a
  body. `mobile/src/api/workers.js:21` sends JSON — 422 on every call.
- **`/admin/analytics` returns `total_in_period`**, not `total_issues`.
  `admin/app/dashboard/analytics/page.js:116` reads the latter, so every PDF
  summary row exports as 0.

`IssueUpdate.priority` / `.department` are the fifth, and the only one the types
*cannot* catch — the field exists and typechecks; it just does nothing.
